# 成果物の状態・版・参照（全工程共通）

各工程の成果物（`brief.md`、`synopsis.md` など）は、内容だけでなく **状態・版・参照関係** を残す。AI は人の承認を捏造しない。

## 状態語彙（必須）

次のいずれかを成果物ヘッダまたは案件メモに書く:

| 状態 | 意味 |
| --- | --- |
| 下書き | 作業中。他工程の確定前提にしてはいけない |
| 人の確認待ち | AI/下書き済み。人の明示確認がまだない |
| 確定 | 人が採用を明示した正本 |
| 要再確認 | 上流が変わった、または指摘修正後。再確認が必要 |

「出荷可能」などの曖昧語は使わない。上記の語彙で書く。

## 公開ステータス（任意公開工程）

成果物の `確定` と、配信・アップロードの状態は **別** に扱う。公開ステータスは次のいずれか（該当する場合）:

| 公開ステータス | 意味 |
| --- | --- |
| 未実施 | まだ公開操作をしていない（またはスコープ外） |
| 承認 | 人が公開してよいと判断した（未アップロードでも可） |
| 保留 | 公開判断を保留している |
| 実施済み | 実際にアップロード／配信した |

成果物を `確定` しても、公開ステータスは自動で `実施済み` にならない。アップロードが工程スコープに入るかは brief／当該工程に明示する。

## 各成果物に残す最小メタ

- **参照:** ファイルパス／版（日付または短い版ラベル）／ページ範囲があればそれ
- **状態:** 上表のいずれか
- **誰が決めたか:** 確定にした人の名前または役割（AI 名は不可）
- **未解決:** 開いている論点・差し戻し（なければ「なし」）
- **公開ステータス:** 任意公開工程の成果なら上表のいずれか（不要なら省略可）

`decided_by` は brief の最終判断者を既定として下流へ引き継ぐ。別の人が
特定成果物を確定した場合だけ、その成果物で上書き理由を残す。

例（成果物先頭）:

```markdown
<!-- process-state
ref: projects/slug/synopsis.md
version: 2026-09-15a
state: 確定
decided_by: 作者
open_issues: なし
upstream: brief@2026-09-14 確定
-->
```

形式は自由でよいが、上記が追跡できればよい。

## 上流変更時の規則

1. 上流成果物を直したら、**依存する下流**の状態を `要再確認` にする（自動で `確定` のままにしない）。
2. 下流を再開するときは差分を見てから再確定する。
3. 典型の依存（目安）:
   - brief → synopsis → pagination ⇄ prose ⇄ rough（反復可）
   - character は rough / final-art の前提
   - visual-refs は rough 途中でも可
   - final-art 前に prose・character・rough が **確定**
   - readthrough → rights-export →（任意）epub / youtube
4. 任意公開工程からの典型の戻り先:
   - EPUB のレイアウト／パッケージ不備 → `picture-book-epub`（必要なら構造のみ再変換）
   - TTS・同期・字幕 → `picture-book-youtube`
   - 本文・絵・構成の中身 → 上流の craft 工程へ戻し、当該成果を `要再確認`
   - 工程内で追加・変更した素材の権利 → rights-export 節A
   - 公開チャネル自体の変更 → `picture-book-brief`

## 成果物と中間生成物の置き場

- 最終成果物は案件の `dist/` を既定の出力先とする。brief が別の納品先を
  明示した場合はその指定を優先し、出力先を案件記録に残す。
- レンダリング画像、変換用一時ファイル、キャッシュは最終成果物に含めず、
  Git 管理対象から除外する。
- `dist/` の各ファイルについて、入力版・生成手順・検証結果を追跡できるようにする。
- 試作と納品版を同じファイル名で混同しない。試作なら用途または版を名前か記録に付ける。

## 短いパス（例外）の記録

brief で工程を省略する短いパスを取る場合は、少なくとも次を残す:

- **対象成果物**（何を正とするか）
- **スキップした工程／手順**
- **人の判断**（誰が、なぜ省略を許したか）

記録なしの省略を「完了」にしない。

## AI の禁止（承認捏造）

- 「確定」「採用」「人OK」と書いてはいけない。人が明示するまで最大でも `人の確認待ち`
- チャット上の曖昧な「よさそう」を確定扱いにしない
- 上流未確定のまま下流を `確定` にしない

## 各工程スキルからの参照

各 `SKILL.md` の前提／完了条件は、本ファイルの状態語彙に従う。完了条件の「確定」は **人の明示** を意味する。公開ステータスは成果物の `確定` と混同しない。
